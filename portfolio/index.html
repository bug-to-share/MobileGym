60 秒项目介绍 · 适合面试开场

我做的是基于 Qwen3-VL 的多模态 GUI Agent 后训练。模型只看任务指令、历史文本和当前截图，输出坐标动作，环境根据业务状态判分。我复用了 MobileGym 和 rLLM/verl，主要扩展了按组内奖励差异补采样的机制、两种奖励分支，以及环境初始化和任务模板重建。

我跑了六组主要探索性实验。其中一次训练，在相同的 256 个验证任务上从 8.98% 提升到最高 21.88%。我也发现有效组变多不一定意味着单位交互预算更好，终止惩罚可能伴随更多 ABORT。下一步会固定评测协议，用等预算、多 seed 对照验证子目标信用分配对跨应用长链任务的帮助。

Q01请用一分钟介绍这个项目项目与多模态+

回答： 我基于 MobileGym 对 Qwen3-VL-4B 做多模态在线强化学习。模型通过截图和语言历史决定 GUI 动作，环境提供可验证奖励。我重点改了动态有效组补采样、严格结果/错误完成奖励，以及环境初始化与模板重建。一次同任务集合的训练从 23/256 成功提升到最高 56/256，同时识别出跨应用长链和终止行为是主要瓶颈。

追问准备： 按“任务与难点—个人改造—结果—限制”组织，避免只列工具名；明确这个数字是单次验证峰值。

Q02开源项目已经有训练栈 你具体做了什么项目与多模态+

回答： 上游已经提供模拟环境、状态判分和基础 GRPO 训练。我增加了按奖励 range 判断有效组、跨 batch 补采样、达到上限后的回退，以及多轮 rollout 结束后再释放推理副本的调度。奖励方面新增 result_only 和错误 COMPLETE 清零；工程方面贯通模板索引，增加分批初始化、首图预热与失败清理。

追问准备： 能打开 unified_trainer、evaluator 和 pool 的改动解释控制流。不要把已有 checkpoint 恢复或 vLLM 本身说成自己实现。

Q03为什么这是多模态后训练项目项目与多模态+

回答： 输入同时含截图和文本指令/历史，模型要把视觉元素定位与语言目标映射成动作序列。训练阶段用环境反馈更新预训练 VLM 的行为策略，属于后训练。我的工作主要是交互策略学习、奖励与采样，没有开发新的视觉编码器或重新做多模态预训练。

追问准备： 说明 grounding、planning、memory 和 termination 四类错误如何区分；不要把所有失败都归为视觉识别。

Q04Agent 会不会读取 DOM 或内部状态作弊项目与多模态+

回答： 当前 generic_v2 构造给模型的输入是任务、历史文本和当前截图，未传入 route、DOM 或业务 state。内部状态用于环境重置与 judge，属于训练监督通道。若以后用状态生成过程标签，也会保持它只用于奖励计算，评测时不把隐藏答案加入 policy 输入。

追问准备： 指出 build_messages 与 judge 的边界。环境 Observation 对象有字段，并不代表模型真的收到这些字段。

Q05训练数据是什么 160 个任务是不是太少项目与多模态+

回答： 标准划分是 160 个训练任务、256 个测试任务，它们指任务类/模板，任务还能采样参数和指令变体。sample_n=4 那次实际产生 443 条训练数据行，受 sample_max 和参数空间约束，并非简单的 640 条。但增加参数实例不等于增加任务家族和技能覆盖，跨应用任务在训练中的比例仍偏低。

追问准备： 任务 ID 不重叠不代表 App 不重叠；历史 test 多次用于开发验证，最终还需要独立 holdout。

Q06为什么选择 4B 模型 8B 跑过吗项目与多模态+

回答： 这次主要沿用上游 Qwen3-VL-4B-Instruct 基线，在可用配置下先研究采样和奖励。4B 方便做多组探索，但我没有做严格的模型规模优劣比较。8B 有两次初始验证，没有完成训练更新，其中存在 NCCL 超时，因此不能把它写成完成了 8B RL，也不能断言更大模型不适合。

追问准备： GPU 型号、训练总时长和峰值显存只报实际测量；6 GPU 配置本身不足以推断这些数值。

Q07为什么使用 RL 而不是只做 SFT项目与多模态+

回答： SFT 学习给定轨迹的动作分布，适合建立格式、grounding 和基本操作能力；在线 RL 可以在交互中探索不同路径，用最终任务反馈优化行为。这个环境可以重置并程序化判分，适合研究 RL。我目前没有完成严格的 SFT-versus-RL 对照，因此不能说 RL 在这个项目中已被证明全面优于 SFT。

追问准备： 无成功探索的长任务可先用训练集示范 warm-start，再以相同 RL 预算比较；示范质量和恢复行为覆盖很重要。

Q08GRPO 与 PPO 的区别是什么强化学习与奖励+

回答： 常见 PPO actor-critic 实现利用价值函数估计优势，并对新旧策略概率比做 clipped surrogate 更新。GRPO 对同任务采样一组输出，用组内奖励均值与尺度构造相对优势，通常省去单独的学习型 value critic。我的实验每任务主要采样 8 条轨迹，使用组内标准化优势，再广播到该轨迹的响应步骤。

A_i ≈ (R_i − mean_group(R)) / (std_group(R) + ε)
rho = πθ(action | history) / πold(action | history)
Jclip = E[min(rho*A, clip(rho, 1−ε_low, 1+ε_high)*A)]

追问准备： 这是核心形式，实际还有 mask、聚合和 KL/熵项。PPO 并非数学上必须有 critic；GRPO 也不等于完全不需要 reference policy。GRPO 原文；PPO 原文

Q09能不能用 DPO 替代 GRPO强化学习与奖励+

回答： 可以构造偏好优化对照，但两者数据条件不同。标准 DPO 使用同一输入下的 preferred/rejected 响应对，通过策略相对 reference 的概率比优化偏好，不需要先训练独立 reward model。GUI 场景中，不同轨迹会看到不同后续截图，构造同条件、可信的动作或轨迹偏好并不简单。当前我利用可在线判分的环境做 GRPO，没有完成 DPO 实验。

追问准备： 可从相同可见前缀的不同动作构造对照，但要控制环境状态与后续采样；不能把“成功轨迹 vs 任意失败轨迹”直接当无偏逐步偏好。DPO 原文

Q10你的 reward 怎么设计 是否使用 PRM强化学习与奖励+

回答： 当前 reward 是规则终态奖励。原有 progress 根据最终通过的目标检查比例给分，并处理终止和副作用；我增加严格成功 0/1 和错误 COMPLETE 清零两个分支。没有逐步学习型评分器，所以不能称为 PRM。即使之后每步用状态规则打分，也应先称为可验证过程奖励。

追问准备： 能区分 reward、progress、goal_success、clean 与 strict success。不要把带部分分数的 reward 自动叫过程奖励模型。

Q11当前信用分配到什么粒度强化学习与奖励+

回答： 当前默认 verl 路径先对每条轨迹的终态奖励算组内优势，再将同一标量赋给该轨迹所有响应步骤。它能比较不同轨迹，但难以直接区分一条轨迹里哪个动作有贡献。一个成功轨迹的冗余步骤也可能得到同号优势；不同 token 的实际梯度仍因概率、clipping 和 mask 不同。

追问准备： Step.reward 当前未被默认优势路径使用，不能只改字段或打开 per_step 就声称完成信用分配。

Q12动态采样具体如何实现 为什么要回退强化学习与奖励+

回答： 对同任务多条轨迹检查奖励是否为有限值，以及 max-min 是否达到阈值。有效组不足时继续生成下一个 batch，直到目标组数、轮数上限或数据耗尽。支持只用有效组、有效组加普通组补齐、按普通 batch 等回退，以避免某些任务分布下长期无法更新。历史主动态实验目标为 12 组，上限 8 轮，实际记录最多 2 轮。

追问准备： 有效组代表存在相对奖励信号，不等于严格成功组。需解释数据游标消耗和 fallback 对分布的影响。

Q13你是不是实现了 DAPO强化学习与奖励+

回答： 准确说是 DAPO-inspired 动态采样扩展。DAPO 还包括 Clip-Higher、token-level policy gradient loss 和 overlong reward 等设计。本地仍使用 GRPO 优势与 seq-mean-token-mean 聚合，多数 run 保留 KL；实验名叫 DAPO 不代表完整复现。

追问准备： 能说清自己改了哪一部分、哪些组件沿用原实现。DAPO 原文

Q14一组轨迹奖励都相同 会发生什么强化学习与奖励+

回答： 组内中心化后，任务奖励对应的相对优势为零。全成功和全失败都可能出现这种情况，进度奖励下也可能全部相同。动态采样希望补充有差异的组。不过即便这个组的任务 policy-gradient 项为零，KL 和 entropy 等正则项仍可能带来梯度，不能说模型完全停止更新。

追问准备： 0/1 奖励下有效组通常混合成功与失败；进度奖励下不同程度的失败也能形成有效组。

Q15KL entropy 和 PPO clipping 有什么不同强化学习与奖励+

回答： reference KL 用来约束当前策略相对参考模型的偏离；entropy 项鼓励分布保留探索性；PPO clipping 则限制当前策略相对采样/旧策略概率比在目标中的激励。它们不等价。项目中多数 run 使用 actor KL loss，不能与 use_kl_in_reward 混为一谈，后者是把 KL 放进奖励的另一条路径。

追问准备： 区分 πref、πold、πθ；KL 更低不自动意味着成功率更高，也不能只看一个 clipfrac 判断稳定性。

Q16mini-batch 12 和 96 到底代表什么强化学习与奖励+

回答： 它们是 PPO mini-batch 配置，不是环境数或 GUI 步数。当前 backend 还乘 rollout.n=8，对应全局目标 96 与 768 个展开的 step-row。每个外层 trainer step 可能包含多个内部 optimizer.step，实际次数依赖轨迹展开长度、过滤和 padding，不能直接用记录的 30 个 trainer step 当 30 次参数更新。

追问准备： 区分任务组、轨迹、GUI step、step-row、micro-batch、optimizer.step。日志没有足够信息时不硬推精确更新次数。

Q17多模态数据和 loss mask 有什么容易出错的地方训练与实现+

回答： 截图和任务历史属于模型条件，策略目标作用于生成的 response token。需要保证图像尺寸处理与动作坐标映射一致，视觉输入和文本 token 顺序一致，padding/观察内容不被误当成动作学习目标。当前 response 中若同时有解释与动作，行级优势会作用于这些生成 token，而不是已经完成了精确的动作字段信用分配。

追问准备： 若截断丢失目标指令、历史动作或图片标记，模型可能学到错误对应。先查实际 processor、response mask 和 trace，不只看 prompt 文本。

Q18FSDP 和 vLLM 各自做什么训练与实现+

回答： FSDP 负责训练侧的参数、梯度和优化器状态分片，按配置降低单卡训练内存压力；vLLM 负责 rollout 推理。我主要使用现有框架，改的是多轮动态采样期间的副本生命周期：生成未结束前保持可用，全部候选收集完成后再 sleep，配合训练更新边界。6 GPU 是历史配置，不代表我实现了这两个引擎。

追问准备： 分片与通信有开销，不能说六卡一定六倍吞吐；权重同步、旧策略 logprob 和 replica 状态需要一致。PyTorch FSDP 文档

Q19你用 LoRA 还是全参数训练 视觉塔更新了吗训练与实现+

回答： 已核对的普通 progress 和 FCzero 正式日志记录 lora_rank=0、freeze_vision_tower=false，属于非 LoRA 的全模型微调配置。按当前代码路径，视觉塔未显式冻结。但没有逐模块梯度或权重差记录，因此我不会宣称已经测得视觉编码器每层都发生有效更新，也没有做冻结与解冻的受控消融。

追问准备： 后续保存 trainable 参数清单、优化器参数组、视觉模块梯度范数与前后权重差。不能仅凭“用了 FSDP”推断训练范围。

Q20如何判断一个任务成功训练与实现+

回答： 严格成功要求所有目标检查通过、没有白名单外的状态修改，并以 COMPLETE 结束。达到目标却一直循环、错误 ABORT，或者改坏其他业务数据，都可能失败。查询类 Grounded 任务需要真实打开答题卡、填写并提交，不能只凭模型文本里说出答案就算成功。

追问准备： 先看固定任务分母的 strict pass@1，再看 progress 和终止类别。查询失败要区分信息读取、记忆和答卷操作。

Q21简历中的提升数字可信在哪里 有什么限制结果与实验+

回答： 8.98%→21.88% 来自 FCzero 同一个 run，23/256→56/256，任务 ID 与题目文本一致，原始结果复核没有环境 ERROR。step0 有一个重复失败记录，按任务去重仍是 23 个成功。但这只是单次训练峰值，完整初态快照不齐全，没有多 seed 和独立最终 holdout，也不是相对普通 GRPO 的因果增益。

追问准备： 说“增加 12.89 个百分点”，不要说“相对提升 12.89%”；能解释为什么总体更高的 22.66% 不能拼接另一 run 的初始分数。

Q22动态采样到底有没有提升结果与实验+

回答： 当前只能说提高了入选组的奖励差异，不能说稳定提高最终成功率。更可比的纯结果两组在健康区间交替领先，动态组平均候选量约为普通的 2.16 倍。动态 progress 那组还改变了验证集合，只覆盖 89 个基础任务，因此不能直接和普通组峰值比较。下一步要固定实例，用相同候选/token 或 GPU 时间预算做对照。

追问准备： 相同 outer step 不等于相同数据、算力或任务覆盖；候选成本必须包括被丢弃的数据。

Q23大 mini-batch 的 KL 更低 为什么成功率没更高结果与实验+

回答： 更大 mini-batch 改变了数据聚合和外层循环内部的优化器调用次数。KL 和 clipfrac 降低说明某些优化统计变化，不代表任务策略更好。M96 的 progress 峰值 21.09%，现有记录未显示一致优势，而且还有任务文本、随机性与验证频率差异。需要明确按候选预算还是实际更新数比较。

追问准备： rollout_probs_diff_mean 是 rollout 与训练侧重算概率差异，发生在本轮更新前，不能把它当成本轮 optimizer 导致的 KL。

Q24验证先升后降 是不是过拟合结果与实验+

回答： 先升后降是现象，原因不能直接确定。可能涉及过拟合、终止行为转移、优化幅度、数据采样变化，也可能是环境故障。FCzero 后期 ABORT 增加；纯结果 GRPO 后期大量 TargetClosedError。应先看固定实例的逐任务变化和错误覆盖，再在健康环境重评已有 checkpoint，而不是把所有下降统一叫过拟合。

追问准备： 变化的训练 batch reward 与固定验证成功率不是同分布曲线，动态组筛选还会引入选择偏差。

Q25错误 COMPLETE 清零为什么没解决终止问题结果与实验+

回答： 这个规则改变的是相对奖励。未完成却 COMPLETE 会归零，但某些 ABORT 轨迹仍可能保留进度奖励，存在转向 ABORT 的激励。记录里 FCzero 后期 ABORT 增多、成功下降，所以我会同时检查严格成功、错误 COMPLETE、ABORT、循环和超时，并先做失败终止口径一致的对照。

追问准备： 这是一种机制假设，不能仅凭聚合曲线断言模型“学会投机”。自动截断也不是模型主动选择停止。

Q26成功率只有约 20% 这个项目有什么价值结果与实验+

回答： 总体分数需要结合任务难度理解。FCzero 峰值的 L1 为 95%，跨应用为 6.45%、L4 为 1.25%，说明基础交互与长链组合的表现差距很大。项目价值在于完成实际训练、实现可解释的改造，并把“哪里失败、为什么暂时不能下结论”追到轨迹和代码。下一步用可验证实验改善瓶颈，而不是把一个总体峰值包装成通用能力。

追问准备： 不用上游论文的真机成绩为个人结果背书；不要声称达到 SOTA。

Q27环境并发和训练故障你怎么处理工程与改进+

回答： 当前增量是环境池分 wave 启动、等待 readiness、首张截图预热以及初始化异常清理，避免部分未就绪环境被发布给训练。历史仍有训练期间浏览器关闭导致的故障，因此这不等于已经实现了全过程自动恢复。我会按任务记录环境 ERROR、重试和最终覆盖，重建坏实例后再比较模型效果。

追问准备： 96/128 是槽位配置，未做吞吐基准不能说提速多少；NCCL timeout 不等于已证明显存 OOM。

Q28如何保证实验复现与验证可信工程与改进+

回答： 固定代码与 diff、模型、任务 ID、模板、参数、初态、解析器、judge 和 resolved step budget；保存训练/评测 seed、依赖版本、reward 环境变量和恢复来源。seed 相同但代码、世界数据或初态变化仍可能产生不同任务。所有组使用相同评测 manifest，历史 test 作为开发集，最终保留未参与调参的 holdout。

追问准备： 当前训练内与独立 benchmark 的步数预算不同，需要统一；恢复还要核对 RNG 与数据游标，能加载 checkpoint 不等于完整复现。

Q29如果继续做信用分配 你会怎样实现工程与改进+

回答： 我会先记录真实执行动作前后的子目标状态，建立 episode、step 与 gateway trace 的唯一对应，再保留 outcome GRPO 并添加小权重的子目标段信用。必要导航即时进度为零，不应统一判错。仅把 progress 差分求和再广播会回到终态信号；必须让实际 step advantage 随动作或阶段改变。当前 PRM 与这条链路都还没有实现。

追问准备： 默认路径忽略 Step.reward；预计算优势映射还存在缺 episode ID 的风险。先关动态采样，避免终态同奖的组被丢掉，再做 λ=0 回归与多 seed 对照。方案细节（历史记录）

Q30如果只给你有限算力 如何设计下一轮实验工程与改进+

回答： 先修复评测与采样边界，再重评已有 checkpoint，复用现成权重。选择一个主假设，例如终止奖励一致性或子目标段信用，固定基础模型、实例、KL、mini-batch 与候选预算，先小 pilot 排错；将最有信息的候选与基线做至少三个训练 seed 的对照。既报严格成功与长链分层，也报真实交互、token、评分成本和环境错误。

追问准备： 负对照与 λ=0 可用固定 batch 的离线数值检查；预先约定选 checkpoint 规则，不比较各组任意时刻最高值。未复现的收益不填进简历。

2.4 最适合写进简历的结果

FCzero 的同一 run，step0、12、18 使用相同的 256 个唯一任务 ID 与题目文本。严格成功数从 23 增至 56，即：

8.98% → 最高 21.88%，提升 12.89 个百分点。

2.5 最有价值的结论

Q07 为什么使用 RL 而不是只做 SFT

回答： SFT 学习给定轨迹的动作分布，适合建立格式、grounding 和基本操作能力；在线 RL 可以在交互中探索不同路径，用最终任务反馈优化行为。这个环境可以重置并程序化判分，适合研究 RL。我目前没有完成严格的 SFT-versus-RL 对照，因此不能说 RL 在这个项目中已被证明全面优于 SFT。

追问准备： 无成功探索的长任务可先用训练集示范 warm-start，再以相同 RL 预算比较；示范质量和恢复行为覆盖很重要。

Q08 GRPO 与 PPO 的区别是什么

回答： 常见 PPO actor-critic 实现利用价值函数估计优势，并对新旧策略概率比做 clipped surrogate 更新。GRPO 对同任务采样一组输出，用组内奖励均值与尺度构造相对优势，通常省去单独的学习型 value critic。我的实验每任务主要采样 8 条轨迹，使用组内标准化优势，再广播到该轨迹的响应步骤。

A_i ≈ (R_i − mean_group(R)) / (std_group(R) + ε)
rho = πθ(action | history) / πold(action | history)
Jclip = E[min(rho*A, clip(rho, 1−ε_low, 1+ε_high)*A)]

追问准备： 这是核心形式，实际还有 mask、聚合和 KL/熵项。PPO 并非数学上必须有 critic；GRPO 也不等于完全不需要 reference policy。GRPO 原文；PPO 原文

Q09 能不能用 DPO 替代 GRPO

回答： 可以构造偏好优化对照，但两者数据条件不同。标准 DPO 使用同一输入下的 preferred/rejected 响应对，通过策略相对 reference 的概率比优化偏好，不需要先训练独立 reward model。GUI 场景中，不同轨迹会看到不同后续截图，构造同条件、可信的动作或轨迹偏好并不简单。当前我利用可在线判分的环境做 GRPO，没有完成 DPO 实验。

追问准备： 可从相同可见前缀的不同动作构造对照，但要控制环境状态与后续采样；不能把“成功轨迹 vs 任意失败轨迹”直接当无偏逐步偏好。DPO 原文

Q10 你的 reward 怎么设计 是否使用 PRM

回答： 当前 reward 是规则终态奖励。原有 progress 根据最终通过的目标检查比例给分，并处理终止和副作用；我增加严格成功 0/1 和错误 COMPLETE 清零两个分支。没有逐步学习型评分器，所以不能称为 PRM。即使之后每步用状态规则打分，也应先称为可验证过程奖励。

追问准备： 能区分 reward、progress、goal_success、clean 与 strict success。不要把带部分分数的 reward 自动叫过程奖励模型。

Q11 当前信用分配到什么粒度

回答： 当前默认 verl 路径先对每条轨迹的终态奖励算组内优势，再将同一标量赋给该轨迹所有响应步骤。它能比较不同轨迹，但难以直接区分一条轨迹里哪个动作有贡献。一个成功轨迹的冗余步骤也可能得到同号优势；不同 token 的实际梯度仍因概率、clipping 和 mask 不同。

追问准备： Step.reward 当前未被默认优势路径使用，不能只改字段或打开 per_step 就声称完成信用分配。

Q12 动态采样具体如何实现 为什么要回退

回答： 对同任务多条轨迹检查奖励是否为有限值，以及 max-min 是否达到阈值。有效组不足时继续生成下一个 batch，直到目标组数、轮数上限或数据耗尽。支持只用有效组、有效组加普通组补齐、按普通 batch 等回退，以避免某些任务分布下长期无法更新。历史主动态实验目标为 12 组，上限 8 轮，实际记录最多 2 轮。

追问准备： 有效组代表存在相对奖励信号，不等于严格成功组。需解释数据游标消耗和 fallback 对分布的影响。

Q13 你是不是实现了 DAPO

回答： 准确说是 DAPO-inspired 动态采样扩展。DAPO 还包括 Clip-Higher、token-level policy gradient loss 和 overlong reward 等设计。本地仍使用 GRPO 优势与 seq-mean-token-mean 聚合，多数 run 保留 KL；实验名叫 DAPO 不代表完整复现。

追问准备： 能说清自己改了哪一部分、哪些组件沿用原实现。DAPO 原文

Q14 一组轨迹奖励都相同 会发生什么

回答： 组内中心化后，任务奖励对应的相对优势为零。全成功和全失败都可能出现这种情况，进度奖励下也可能全部相同。动态采样希望补充有差异的组。不过即便这个组的任务 policy-gradient 项为零，KL 和 entropy 等正则项仍可能带来梯度，不能说模型完全停止更新。

追问准备： 0/1 奖励下有效组通常混合成功与失败；进度奖励下不同程度的失败也能形成有效组。

Q15 KL entropy 和 PPO clipping 有什么不同

回答： reference KL 用来约束当前策略相对参考模型的偏离；entropy 项鼓励分布保留探索性；PPO clipping 则限制当前策略相对采样/旧策略概率比在目标中的激励。它们不等价。项目中多数 run 使用 actor KL loss，不能与 use_kl_in_reward 混为一谈，后者是把 KL 放进奖励的另一条路径。

追问准备： 区分 πref、πold、πθ；KL 更低不自动意味着成功率更高，也不能只看一个 clipfrac 判断稳定性。

Q16 mini-batch 12 和 96 到底代表什么

回答： 它们是 PPO mini-batch 配置，不是环境数或 GUI 步数。当前 backend 还乘 rollout.n=8，对应全局目标 96 与 768 个展开的 step-row。每个外层 trainer step 可能包含多个内部 optimizer.step，实际次数依赖轨迹展开长度、过滤和 padding，不能直接用记录的 30 个 trainer step 当 30 次参数更新。

追问准备： 区分任务组、轨迹、GUI step、step-row、micro-batch、optimizer.step。日志没有足够信息时不硬推精确更新次数。

Q17 多模态数据和 loss mask 有什么容易出错的地方

回答： 截图和任务历史属于模型条件，策略目标作用于生成的 response token。需要保证图像尺寸处理与动作坐标映射一致，视觉输入和文本 token 顺序一致，padding/观察内容不被误当成动作学习目标。当前 response 中若同时有解释与动作，行级优势会作用于这些生成 token，而不是已经完成了精确的动作字段信用分配。

追问准备： 若截断丢失目标指令、历史动作或图片标记，模型可能学到错误对应。先查实际 processor、response mask 和 trace，不只看 prompt 文本。

Q18 FSDP 和 vLLM 各自做什么

回答： FSDP 负责训练侧的参数、梯度和优化器状态分片，按配置降低单卡训练内存压力；vLLM 负责 rollout 推理。我主要使用现有框架，改的是多轮动态采样期间的副本生命周期：生成未结束前保持可用，全部候选收集完成后再 sleep，配合训练更新边界。6 GPU 是历史配置，不代表我实现了这两个引擎。

追问准备： 分片与通信有开销，不能说六卡一定六倍吞吐；权重同步、旧策略 logprob 和 replica 状态需要一致。PyTorch FSDP 文档

Q19 你用 LoRA 还是全参数训练 视觉塔更新了吗

回答： 已核对的普通 progress 和 FCzero 正式日志记录 lora_rank=0、freeze_vision_tower=false，属于非 LoRA 的全模型微调配置。按当前代码路径，视觉塔未显式冻结。但没有逐模块梯度或权重差记录，因此我不会宣称已经测得视觉编码器每层都发生有效更新，也没有做冻结与解冻的受控消融。

追问准备： 后续保存 trainable 参数清单、优化器参数组、视觉模块梯度范数与前后权重差。不能仅凭“用了 FSDP”推断训练范围。

Q20 如何判断一个任务成功

回答： 严格成功要求所有目标检查通过、没有白名单外的状态修改，并以 COMPLETE 结束。达到目标却一直循环、错误 ABORT，或者改坏其他业务数据，都可能失败。查询类 Grounded 任务需要真实打开答题卡、填写并提交，不能只凭模型文本里说出答案就算成功。

追问准备： 先看固定任务分母的 strict pass@1，再看 progress 和终止类别。查询失败要区分信息读取、记忆和答卷操作。

Q21 简历中的提升数字可信在哪里 有什么限制

回答： 8.98%→21.88% 来自 FCzero 同一个 run，23/256→56/256，任务 ID 与题目文本一致，原始结果复核没有环境 ERROR。step0 有一个重复失败记录，按任务去重仍是 23 个成功。但这只是单次训练峰值，完整初态快照不齐全，没有多 seed 和独立最终 holdout，也不是相对普通 GRPO 的因果增益。

追问准备： 说“增加 12.89 个百分点”，不要说“相对提升 12.89%”；能解释为什么总体更高的 22.66% 不能拼接另一 run 的初始分数。

Q22 动态采样到底有没有提升

回答： 当前只能说提高了入选组的奖励差异，不能说稳定提高最终成功率。更可比的纯结果两组在健康区间交替领先，动态组平均候选量约为普通的 2.16 倍。动态 progress 那组还改变了验证集合，只覆盖 89 个基础任务，因此不能直接和普通组峰值比较。下一步要固定实例，用相同候选/token 或 GPU 时间预算做对照。

追问准备： 相同 outer step 不等于相同数据、算力或任务覆盖；候选成本必须包括被丢弃的数据。

Q23 大 mini-batch 的 KL 更低 为什么成功率没更高

回答： 更大 mini-batch 改变了数据聚合和外层循环内部的优化器调用次数。KL 和 clipfrac 降低说明某些优化统计变化，不代表任务策略更好。M96 的 progress 峰值 21.09%，现有记录未显示一致优势，而且还有任务文本、随机性与验证频率差异。需要明确按候选预算还是实际更新数比较。

追问准备： rollout_probs_diff_mean 是 rollout 与训练侧重算概率差异，发生在本轮更新前，不能把它当成本轮 optimizer 导致的 KL。

Q24 验证先升后降 是不是过拟合

回答： 先升后降是现象，原因不能直接确定。可能涉及过拟合、终止行为转移、优化幅度、数据采样变化，也可能是环境故障。FCzero 后期 ABORT 增加；纯结果 GRPO 后期大量 TargetClosedError。应先看固定实例的逐任务变化和错误覆盖，再在健康环境重评已有 checkpoint，而不是把所有下降统一叫过拟合。

追问准备： 变化的训练 batch reward 与固定验证成功率不是同分布曲线，动态组筛选还会引入选择偏差。

Q25 错误 COMPLETE 清零为什么没解决终止问题

回答： 这个规则改变的是相对奖励。未完成却 COMPLETE 会归零，但某些 ABORT 轨迹仍可能保留进度奖励，存在转向 ABORT 的激励。记录里 FCzero 后期 ABORT 增多、成功下降，所以我会同时检查严格成功、错误 COMPLETE、ABORT、循环和超时，并先做失败终止口径一致的对照。

追问准备： 这是一种机制假设，不能仅凭聚合曲线断言模型“学会投机”。自动截断也不是模型主动选择停止。

Q26 成功率只有约 20% 这个项目有什么价值

回答： 总体分数需要结合任务难度理解。FCzero 峰值的 L1 为 95%，跨应用为 6.45%、L4 为 1.25%，说明基础交互与长链组合的表现差距很大。项目价值在于完成实际训练、实现可解释的改造，并把“哪里失败、为什么暂时不能下结论”追到轨迹和代码。下一步用可验证实验改善瓶颈，而不是把一个总体峰值包装成通用能力。

追问准备： 不用上游论文的真机成绩为个人结果背书；不要声称达到 SOTA。

Q27 环境并发和训练故障你怎么处理

回答： 当前增量是环境池分 wave 启动、等待 readiness、首张截图预热以及初始化异常清理，避免部分未就绪环境被发布给训练。历史仍有训练期间浏览器关闭导致的故障，因此这不等于已经实现了全过程自动恢复。我会按任务记录环境 ERROR、重试和最终覆盖，重建坏实例后再比较模型效果。

追问准备： 96/128 是槽位配置，未做吞吐基准不能说提速多少；NCCL timeout 不等于已证明显存 OOM。

Q28 如何保证实验复现与验证可信

回答： 固定代码与 diff、模型、任务 ID、模板、参数、初态、解析器、judge 和 resolved step budget；保存训练/评测 seed、依赖版本、reward 环境变量和恢复来源。seed 相同但代码、世界数据或初态变化仍可能产生不同任务。所有组使用相同评测 manifest，历史 test 作为开发集，最终保留未参与调参的 holdout。

追问准备： 当前训练内与独立 benchmark 的步数预算不同，需要统一；恢复还要核对 RNG 与数据游标，能加载 checkpoint 不等于完整复现。

Q29 如果继续做信用分配 你会怎样实现

回答： 我会先记录真实执行动作前后的子目标状态，建立 episode、step 与 gateway trace 的唯一对应，再保留 outcome GRPO 并添加小权重的子目标段信用。必要导航即时进度为零，不应统一判错。仅把 progress 差分求和再广播会回到终态信号；必须让实际 step advantage 随动作或阶段改变。当前 PRM 与这条链路都还没有实现。

追问准备： 默认路径忽略 Step.reward；预计算优势映射还存在缺 episode ID 的风险。先关动态采样，避免终态同奖的组被丢掉，再做 λ=0 回归与多 seed 对照。方案细节（历史记录）

Q30 如果只给你有限算力 如何设计下一轮实验

回答： 先修复评测与采样边界，再重评已有 checkpoint，复用现成权重。选择一个主假设，例如终止奖励一致性或子目标段信用，固定基础模型、实例、KL、mini-batch 与候选预算，先小 pilot 排错；将最有信息的候选与基线做至少三个训练 seed 的对照。既报严格成功与长链分层，也报真实交互、token、评分成本和环境错误。

追问准备： 负对照与 λ=0 可用固定 batch 的离线数值检查；预先约定选 checkpoint 规则，不比较各组任意时刻最高值。未复现的收益不填进简历。

6.2 第二优先级 做一个可解释的算法改进

建议主问题：可验证子目标信用能否在相同交互预算下提高跨应用与 L3/L4 成功率？

按阶段推进：

  1. 先做诊断。 抽取长链失败轨迹，标记首个错误：定位、搜索、记忆、跨 App 状态、业务操作、答卷、终止。不能在没有分类的情况下假设所有失败都需要 PRM。
  2. 修正终止激励。 比较错误 COMPLETE 与未完成 ABORT 的一致奖励口径，检查是否只是从一种失败转移到另一种。
  3. 增加步骤数据。 当前 env.get_state() 仍取完整状态，需要测开销；为步骤保存执行标记、子目标前后值、唯一 trace ID，正确处理循环检测前未执行的动作。
  4. 接真实过程优势。 采用 A_step=A_outcome+λ*C_segment 等清晰可消融设计，先让 λ=0 复现原优势。该混合项是待验证辅助目标，不自动无偏。
  5. 测同状态锚点。 GiGPO 式对照可复用现有 rollout，但必须检查 GUI 隐藏状态、历史与剩余预算的可比性；没有中后段覆盖就不强行推广。

首轮关闭动态筛选，因为现有筛选只看终态奖励差异，可能丢弃含有效过程信号的全失败组。过程方案有效后，再研究二者组合。

6.4 最小正式实验方案

  • 基线： 固定初始 checkpoint 与严格 outcome GRPO，或预先选定的 progress 基线。
  • 候选： 只增加一个信用或终止改动，其余配置相同。
  • 预算： 固定真实候选轨迹/token，并另报总 GPU 时间与 judge 成本。
  • 随机性： pilot 排错后，基线和候选各至少 3 个训练 seed；这是提高可信度的起点，不等于统计功效保证。
  • 评测： 相同实例、预算、评测频率与 checkpoint 选择规则；独立最终 holdout。
  • 报告： 每 seed、均值和波动，严格成功、跨 App、L3/L4、终止分布、环境错误、候选数和成本；按任务/家族做配对分析。

如果过程分数提高但严格成功没提高，或 ABORT 增多，应回到激励和标签诊断。不能只挑一个最好看的指标宣布方法有效。

9.2 如何理解 GUI Agent 这个任务

9.2.1 它是带目标的部分可观测决策问题

可以用以下形式理解：

隐藏状态 s_t：业务数据、页面、导航栈、键盘、焦点、权限、未显示的信息等
观察 o_t：当前截图；具体系统也可能开放 DOM / accessibility tree
可见历史 h_t：(o_0, a_0, …, o_t)，或该历史的受控摘要
目标 g：用户要求及约束
策略 πθ(a_t | g, h_t)：决定操作、查看、等待、恢复或终止
环境转移：执行 a_t 后得到 s_(t+1)，再产生新观察

同一截图可能对应不同隐藏状态；环境转移即使确定，也不意味着模型完全知道状态。目标可能要求先读取信息，再在另一 App 中使用，当前画面不足以决定动作。POMDP 视角可从 OSWorld 与 Agent S2 的形式化出发，但上面的具体变量解释是针对本项目的建模。OSWorld、Agent S2

在本地 MobileGym 中，generic_v2 使用当前截图和历史文本。judge 能读取业务状态，是环境的监督能力；它不意味着 policy 也读取了该状态。训练与评测必须分别写清楚：

通道 能看到什么 作用
Policy 输入 指令、当前图、允许的可见历史 产生动作
执行器 动作参数与环境接口 将动作落实为点击、输入等
Reward / judge 任务条件、初态与结果状态 评分、成功判断、副作用检查
诊断 oracle 人工子目标、正确元素框等额外信息 仅用于定位瓶颈，单独报告
9.2.2 六种能力共同决定完整任务成功
  1. Grounding： 已经知道要找哪个元素，能否定位到正确位置？
  2. Planning： 根据目标和进度，此时应该执行哪个业务操作？
  3. State tracking： 上一步是否生效，页面是否仍在加载，实际对象是谁？
  4. Memory： 跨页面和跨 App 后，能否保留正确实体、数值与约束？
  5. Recovery： 操作失败或进入错误页面后，能否识别并恢复？
  6. Termination： 什么时候应继续、核验、完成或中止？

例如“把聊天中确认的会议地址加入日历”，可能先涉及信息读取，再涉及跨 App 记忆、字段输入和保存验证。点击位置全部正确，也可能因为日期记错而失败。这是示意任务，不是新增实验。

可以用一个简化算式解释长链困难：若每个关键决策的条件成功率都为 95%，20 个关键决策全部成功约为 0.95²⁰＝35.85%。这是恒定条件成功率、无恢复的教学模型，不是项目成功率预测；真实错误存在依赖，恢复操作也会改变结果。

9.2.3 优化目标应同时考虑结果、成本和约束

当前项目的严格成功要求目标达成、没有不允许的副作用并正确 COMPLETE。产品层面还需考虑交互次数、推理 token、延迟和可恢复性。一个实用研究目标是：

在固定交互与计算预算、相同观测/动作接口下，提高严格任务成功率；
同时报告成本、终止分布、环境错误和非预期状态修改。

不要直接用“最短轨迹”替代成功：检查信息、等待加载和纠错可能需要合理的额外操作。也不要一开始把许多成本项混成单个奖励；先测清它们与成功的关系，再用消融决定权重。

9.5 Reward、PRM 与信用分配 应该怎么区分

9.5.1 先回答你当前的 reward 是什么

本项目当前是规则终态奖励：根据最终目标检查、终止类型和副作用等计算轨迹分数。progress 能给部分分，但这仍然是终态结果分解。严格 result_only 与错误 COMPLETE 清零是已有本地分支。

默认 verl 路径读取 trajectory reward，计算组内优势，再广播到同条轨迹的响应步骤。Step.reward 的存在不代表该值已经参与默认优势计算。本地优势路径

  • GiGPO： 在 episode 组之外寻找可比较的 anchor state 组，增加局部相对优势。v3 还包含视觉小环境附录实验，但不是移动 GUI 证据；截图相似也不足以证明状态、历史和剩余预算相同。GiGPO

9.5.3 为什么把 progress 做差分还不够

设 p_t 为第 t 步后的子目标进度。若定义：

r_t = p_t − p_(t−1)
Σ_t r_t = p_T − p_0

求和会消去中间项。如果仍把这个总和变成一个轨迹优势并广播，步骤间依旧没有由过程进度产生的差异化优势；共享同一个优势值，并不意味着不同步骤的策略梯度相同。要完全复现旧奖励，还须保留初始进度以及原先的终止、答案和副作用处理；不能把上式直接当现有 reward 的等价改写。

势函数塑形的标准形式是 F_t＝γΦ(s_(t+1))−Φ(s_t)。折扣求和后为 −Φ(s_0)＋γ^TΦ(s_T)。在相同起点、终止势为零等条件下，它只是一个常数；继续用于组内终态广播时可能被中心化抵消。一般的正向进度奖金并不自动拥有策略不变性保证。Ng、Harada 与 Russell，1999

9.5.4 四条真正需要比较的信用路线
路线 如何区分步骤贡献 代价与风险
子目标段信用 将可验证子目标变化归入对应执行片段 切段质量；必要导航零即时进度；改变辅助目标
Value / GAE 根据可见历史估计未来回报，形成时序差分优势 价值误差、额外训练与显存、稀疏回报
Anchor-state 局部分组 比较足够相近决策条件下的不同后续结果 重复状态覆盖低、隐藏状态混淆、条件不等价
同前缀分叉 rollout 在可恢复状态上尝试不同动作并估计后续成功 克隆真实性、Monte Carlo 成本、后续策略偏差

本项目优先研究第一条。一个可消融的起点是：

A_(episode,t) = A_outcome(episode) + λ · C_segment(episode,t)

C_segment 要有明确的事件定义、范围和归一化规则；λ＝0 必须恢复原数值与 mask。该式是待验证的混合辅助目标，不宣称无偏或保证最优策略不变。

落地要贯通“执行前后记录 → episode/step/trace 唯一映射 → advantage → response mask”。循环检测有可能在 env.step 之前退出，最后生成动作未实际执行；这类事件必须单列。第一轮先关闭只看终态奖励差异的动态筛选，否则含过程差异的同终态组可能被丢掉。

中间态分叉应先验证 UI、业务状态、导航栈、焦点、键盘和时钟恢复。MobileGym 论文描述的 snapshot/fork 能力，不等于当前训练入口已经验证任意中途状态的精确复现。MobileGym

9.6.3 如果要做课程与样本效率优化

WebRL 提供失败驱动的课程与回放思路；MobileRL 把成功轨迹长度、困难正例与难度过滤结合。它们的输入接口和优化器都与当前路径不同，适合拆成单因素实验。WebRL、MobileRL

建议按任务家族、跨 App 与难度分层采样，保留最难层的最低探索配额。仅对成功轨迹奖励效率，防止提前 ABORT 因长度短而获益。若引入历史正例回放，应保存行为策略信息并明确 off-policy 处理；不能把不同策略的旧轨迹直接当成当前同组 rollout。补采样减少了无效更新，也可能增加大量环境开销，必须同时看动作、token、GPU 时间和总墙钟时间。

9.7 怎样证明优化有效 评测应如何设计

9.7.1 至少区分四层泛化
层次 划分单位 回答的问题
参数泛化 同任务族的新实体、金额、日期和随机初态 是否记住具体答案或对象？
模板/任务族泛化 未参与训练和选点的任务语义组合 能否组合已有技能？
App/界面泛化 未见 App、布局变化、主题、语言、分辨率 视觉和操作规则能否迁移？
平台/真实环境迁移 浏览器模拟器到 Android/桌面等 是否依赖模拟器时延、布局或状态规则？

这四种难度不构成普遍严格排序。task ID 不相交只证明 ID 层面的分离；模板、业务流程、画面或生成器仍可能重合。当前反复用于选点的验证集应当视为开发集，另冻结一个最终测试集。所有数据生成器、PRM 标签和课程筛选都不能读取其答案或结果来调参。

9.7.2 统一报告表
维度 应报告的内容
主结果 固定预算下 strict pass@1，成功数/总数；按任务族、单/跨 App、难度分层
部分进度 与严格成功并列，说明终态 check 的语义，不能换名为成功率
稳定性 多训练 seed 的均值/离散度；同 checkpoint 多环境初态的重复测量
错误与终止 ERROR、超时、循环、ABORT、false-COMPLETE；统一保留总体分母
效率 环境动作、生成/输入 token、墙钟时间、GPU 小时、PRM/teacher 调用；包含丢弃 rollout
恢复 固定扰动下成功率、额外动作；同时保留正常起点主结果
搜索 候选数、重试数、verifier 选择规则；与单次策略执行分开报告
选择过程 checkpoint 选择规则、验证次数、停止规则；避免只挑最好点
能力保持 固定 grounding/动作集、简单任务和长任务，检查后训练的能力退化

相同动作预算不等于相同计算预算，候选重排与多图历史尤其如此。可以同时给“同动作预算”和“同 token/GPU 成本”两条性能曲线，寻找成本—成功率的折中。成功轨迹平均长度有幸存者偏差，应同时报告全体 episode 的动作数和失败终止分布。

配对任务 bootstrap 可以估计任务采样的不确定性；有模板相关性时按任务家族做 cluster bootstrap 更合理。它不能替代训练 seed 的方差，也不能把一次训练的多个 checkpoint 当独立训练样本。pass@k 要明确重复采样和候选选择条件；单次成功率不能在不满足条件时直接换算为真实多次尝试能力。

9.7.3 Judge 与环境也是实验对象

基于状态的规则 judge 可检查真实业务结果，但仍可能存在遗漏。应设计少量针对性的反例：错误对象、只改页面不改数据、完成后撤销、重复执行、部分字段正确、提前 COMPLETE、跨 App 副作用。对照人工轨迹审计，检查假阳性与假阴性。

完整重置应验证业务状态、导航栈、焦点、键盘、模拟时间和权限等。评测时隐藏状态可由 judge 使用；若把隐藏状态直接传给 actor，必须另标输入协议。只统计“环境正常”的成功率会掩盖系统可靠性：可补充条件分析，但主表仍保留所有预先指定任务和失败原因。

9.8 值得延伸思考的方向

9.8.1 端到端模型还是模块化系统

SeeClick/UGround 把定位作为可训练接口，Agent S2 强调分层规划与专家模块；UI-TARS 系列则探索更统一的视觉动作模型。模块化方便定位错误、替换 grounder 和控制成本，但模块之间的目标描述可能丢信息；端到端减少手工接口，也更难区分能力瓶颈。UGround、Agent S2、UI-TARS

对本项目可先保持同一个 4B actor，增加可审计的任务记忆与动作结果记录；若确认大多数错误来自定位，再考虑专门 grounder。比较时固定高层计划，并把额外模型、调用次数与延迟计入成本。

9.8.2 有 API 还需要 GUI Agent 吗

GUI 为没有开放 API 或业务接口不统一的应用提供可见操作入口；API 则能减少部分操作的歧义和步数。二者可以组成混合系统，但动作空间与可靠性条件变了。

OpenMobile2 将模拟移动环境、模拟器环境和 App 原生工具结合，适合作为“纯视觉基准之外的产品路线”阅读。其工具调用成绩不能直接作为纯截图坐标策略的同协议比较；MobileGym 中供任务初始化/判题的内部 API 也不是 actor 自动获准使用的工具。OpenMobile2

可以设计独立实验：纯 GUI、GUI+同范围公开工具、工具失败后的 GUI fallback。比较严格完成、时延、工具权限、失败可恢复性，而不是只用动作数更少证明模型能力更强。

9.8.3 既然有模拟器，还要不要学 world model

WM-R1 用学习的 GUI 世界模型生成可交互的后续状态，并支持想象与策略学习。这能扩充训练交互，但策略收益受转移预测、渲染一致性和结果评价误差影响；生成画面像真的，不代表业务状态真的正确。WM-R1

MobileGym 已有程序实现的环境和结构化状态，当前先利用可验证的真实环境 rollout 通常更直接。若长尾 App 或真实设备交互昂贵，再考虑 learned world model，并做“一步预测一致性→多步漂移→真实环境策略收益”的逐级检验。世界模型中的成功率不能替代真实或程序环境成功率；训练策略还可能主动利用模型漏洞。

9.8.4 Sim-to-real 的关键是覆盖什么差异

需要分别检查布局/字体、设备尺寸、软键盘、异步等待、系统弹窗、权限、网络错误、应用状态和动作时延。对这些因素做可控随机化，有助于研究稳健性；随机化范围应来自目标设备的实际差异，过度随机化也会增加学习难度。

MobileGym 论文对其自身平台的迁移证据不等于你的 checkpoint 已完成真实设备验证。简历应保留“浏览器模拟移动环境”口径；有相同任务语义、明确映射和真实设备复测后，再写 sim-to-real 结果。MobileGym

9.8.5 不确定性、停止和交互安全

停止也是动作选择的一部分。模型应能区分“完成证据充分”“仍可恢复”“无法完成”；仅增加 ABORT 惩罚可能诱发胡乱点击，仅惩罚 false-COMPLETE 也可能增加放弃。应同时观察严格成功、误报、漏报、恢复和成本。

在真实应用中，页面内容还可能包含与用户目标冲突的指令；可研究将页面视为数据、限制高影响操作、在不确定时请求用户确认。但这应另设任务与威胁模型，本项目尚未验证相关能力，不能写成已经实现的安全保障。

9.9 面试延伸问答 12 个能展开讨论的问题

以下 R01–R12 是在前面 30 个项目问答之外新增的研究问题。回答用“已经观察到什么—如何解释—如何证伪”组织；涉及改进时明确是计划。

R01 你怎样定义 GUI Agent，它和普通视觉问答有什么不同？

回答思路： 它是通过有限观察持续改变环境状态的决策任务。截图只显示状态的一部分，动作会影响后续可见信息、可执行选项和最终业务结果，所以要联合考虑 grounding、状态估计、计划、恢复和终止。视觉问答主要评价当前答案，GUI 还要评价整段交互的结果与代价。

追问准备： 用跨 App 复制联系人信息举例：源页面离开后关键信息不可见，记忆直接影响后续动作。可对照当前截图、近期多图和结构化记忆；不能只因为跨 App 分数低就断言记忆不足。

R02 Grounding 准确率很高，为什么整任务成功率仍然很低？

回答思路： “点中了所说的按钮”不保证“这个按钮是当前该点的”。还存在目标理解、动作顺序、隐藏状态、执行时序和终止错误。长序列会积累失败风险，但独立同分布误差模型只是解释用的简化。

追问准备： 将动作意图与坐标分开标注，使用正确意图/坐标的诊断对照，找最早偏离点。不要把离线 point-in-box 指标和在线 strict pass@1 放在一个榜单排序。

R03 给模型更多历史截图一定更好吗？

回答思路： 历史可能补充页面变化和已离开的实体，也会带来视觉 token、干扰和上下文压缩问题。关键是保留与当前决策相关的证据，而不只是增加窗口长度。

追问准备： 冻结 actor 比较文本历史、最近截图、结构化记忆、混合记忆；测跨 App 成功、事实保持与成本。记忆摘要应标注来源步骤和置信度，错误信息需要可更新；不能把 ground-truth 隐藏状态写进纯视觉记忆。

R04 SFT、DPO 和在线 RL 分别适合解决什么？

回答思路： SFT 建立接口、基础技能和恢复行为；DPO 需要同一上下文下可解释的偏好对；在线 RL 在可执行环境中直接优化结果和交互决策。三者的数据来源与失败模式不同，不能用算法名称替代问题诊断。

追问准备： 如果格式错误很多，先做数据与 SFT；基础行为可用但完整任务欠佳，再考虑在线反馈。UI-TARS 的 Agent DPO、InfiGUI-R1 的 RLOO 与 UI-TARS-2 的 PPO 应准确区分，不能统称 GRPO。

R05 你现在的 reward 是 PRM 吗？有部分分为何还不算？

回答思路： 当前是最终状态的规则评分，可以给部分目标达成分，但没有使用学习得到的过程评分器。PRM 需要说明训练数据、预测对象与使用位置，也可以复用已有评分模型；逐步调用一个终态检查也只是规则过程信号。

追问准备： 继续检查 reward 怎样进入 advantage。当前路径将轨迹优势广播；即使新增 Step.reward 字段，也要贯通训练消费链路，才能声称实现逐步信用。

R06 为什么把 progress 相邻作差，不一定改进信用分配？

回答思路： 差分求和仍是终点减起点，如果最后又变成一个轨迹标量并广播，没有新增由过程进度产生的动作优势差异；各动作本身的梯度仍可能不同。信用分配要使不同决策获得不同的回报估计或 baseline。

追问准备： 画出 reward→return→advantage→token mask 的链路，给出 telescoping 等式。势函数塑形的策略不变性有条件；新局部辅助项应做零系数一致性与副作用审计。

R07 同一截图下比较动作，是否就是 GiGPO？

回答思路： 不够。GiGPO 的局部比较依赖足够可比的决策状态与后续 return。相同截图可能对应不同表单草稿、任务参数、历史信息或剩余预算；视觉相似可能制造错误的优势。

追问准备： 先统计可靠 anchor 的覆盖、不同轨迹数和 return 方差。若严格匹配后覆盖很低，就转向子目标段或 value；不能通过随意粗化状态来获得漂亮覆盖率。其视觉小环境实验也不能直接证明手机 GUI 迁移。

R08 为什么不直接训练一个更大的 PRM？

回答思路： 更大的模型不会自动消除标签含糊、隐藏信息缺失和奖励利用。当前环境已经能提供可验证状态，先证明过程标签优于 outcome 基线，再判断是否需要把它蒸馏为图像评分器。

追问准备： PRM 离线相关性、校准、候选排序和在线策略收益分别测。冻结 actor 的重排收益包含额外搜索预算；AgentPRM 的末步轨迹奖励实验也不能当作 dense 更新证据。

R09 当前实验支持哪些结论，不支持哪些？

回答思路： 同一 FCzero run 在固定任务 ID 与题目文本下，从 23/256 到峰值 56/256，支持该次训练过程中验证表现改善。跨 App 与高难任务仍弱，后期回落提示稳定性和终止行为值得追踪。

追问准备： 不能由此证明 FCzero 优于普通 GRPO，不能报多 seed 稳定提升，也不能把六组配置差异较大的历史 run 当严格消融。补做共同初始化、同协议、等预算对照及新 hold-out。

R10 多采几个候选再让 verifier 选，算性能优化吗？

回答思路： 算系统推理优化，但要分别报告额外计算收益和 policy 参数更新收益。候选、重试和环境回退次数都应纳入预算，且 selector 只能使用协议允许的信息。

追问准备： 比较单次 actor、同候选数随机选择、verifier 选择，使用相同初态和预算；没有可恢复状态时，不能假装各候选都在同一状态真实执行过。

R11 如果面试官说模拟器太简单，你怎么回答？

回答思路： 模拟器的价值是可控初态、状态判题、可复现交互和低成本实验，适合研究后训练机制。它与真实设备在异步、布局、应用业务和错误分布上可能不同，需要单独验证外部有效性。

追问准备： 先在模拟器内做受控扰动与 held-out App，再选有明确任务对应关系的真实设备测试。当前应坦诚尚未得到本 checkpoint 的真实设备迁移结果。

R12 资源只够再做两组实验，你会怎么选？

回答思路： 先修到冻结基线可复现，这是测量前提。然后根据失败审计选一个主因素：若信息丢失占主因，做原历史 vs 近期多图/记忆；若过程监督明确且映射可靠，做原 GRPO vs 单一局部信用项。

追问准备： 固定 task、初态、初始化、奖励和预算，预先指定 strict pass@1 与跨 App 分层结果，报告成本和失败模式。两组、单 seed 的结果只用于方向筛选，不承诺统计显著或最终产品收益。

9.10 阅读路线、来源与检索边界

9.10.1 建议按问题阅读，而不是背排行榜
  1. 任务是什么： AndroidWorld + MobileGym。先看 observation/action、初始化、judge 与预算，画出训练闭环。
  2. 模型究竟哪里出错： SeeClick + ScreenSpot-Pro + UGround。理解 grounding 的独立指标与高分辨率条件。
  3. 数据如何成为能力： UI-TARS + OSGenesis。区分生成指令、获得成功轨迹、恢复数据与偏好对的成本。
  4. 在线训练怎样改变行为： DigiRL + MobileRL + UI-TARS-2。比较 value/AWR、轨迹 GRPO 与 PPO/GAE；核对输入协议。
  5. 怎样给动作分配信用： GiGPO + GUI-Shepherd + AgentPRM。追踪标签、奖励、advantage 和推理使用方式。
  6. 研究边界如何扩展： Agent S2 + OSWorld2 + OpenMobile2 + WM-R1。讨论长任务、模块化、混合工具与世界模型。

每篇建议做一张卡：任务/接口、监督来源、算法实际更新、主指标、额外成本、最关键限制、一个可迁移实验。面试重点是说明为什么选择某种机制，以及什么证据会让你放弃它。

9.2如何理解 GUI Agent 这个任务+

9.2.1 它是带目标的部分可观测决策问题

可以用以下形式理解：

隐藏状态 s_t：业务数据、页面、导航栈、键盘、焦点、权限、未显示的信息等
观察 o_t：当前截图；具体系统也可能开放 DOM / accessibility tree
可见历史 h_t：(o_0, a_0, …, o_t)，或该历史的受控摘要
目标 g：用户要求及约束
策略 πθ(a_t | g, h_t)：决定操作、查看、等待、恢复或终止
环境转移：执行 a_t 后得到 s_(t+1)，再产生新观察

同一截图可能对应不同隐藏状态；环境转移即使确定，也不意味着模型完全知道状态。目标可能要求先读取信息，再在另一 App 中使用，当前画面不足以决定动作。POMDP 视角可从 OSWorld 与 Agent S2 的形式化出发，但上面的具体变量解释是针对本项目的建模。OSWorld、Agent S2

在本地 MobileGym 中，generic_v2 使用当前截图和历史文本。judge 能读取业务状态，是环境的监督能力；它不意味着 policy 也读取了该状态。训练与评测必须分别写清楚：

通道 能看到什么 作用
Policy 输入 指令、当前图、允许的可见历史 产生动作
执行器 动作参数与环境接口 将动作落实为点击、输入等
Reward / judge 任务条件、初态与结果状态 评分、成功判断、副作用检查
诊断 oracle 人工子目标、正确元素框等额外信息 仅用于定位瓶颈，单独报告

9.2.2 六种能力共同决定完整任务成功

  1. Grounding： 已经知道要找哪个元素，能否定位到正确位置？
  2. Planning： 根据目标和进度，此时应该执行哪个业务操作？
  3. State tracking： 上一步是否生效，页面是否仍在加载，实际对象是谁？
  4. Memory： 跨页面和跨 App 后，能否保留正确实体、数值与约束？
  5. Recovery： 操作失败或进入错误页面后，能否识别并恢复？
  6. Termination： 什么时候应继续、核验、完成或中止？

例如“把聊天中确认的会议地址加入日历”，可能先涉及信息读取，再涉及跨 App 记忆、字段输入和保存验证。点击位置全部正确，也可能因为日期记错而失败。这是示意任务，不是新增实验。

可以用一个简化算式解释长链困难：若每个关键决策的条件成功率都为 95%，20 个关键决策全部成功约为 0.95²⁰＝35.85%。这是恒定条件成功率、无恢复的教学模型，不是项目成功率预测；真实错误存在依赖，恢复操作也会改变结果。

9.2.3 优化目标应同时考虑结果、成本和约束

当前项目的严格成功要求目标达成、没有不允许的副作用并正确 COMPLETE。产品层面还需考虑交互次数、推理 token、延迟和可恢复性。一个实用研究目标是：

在固定交互与计算预算、相同观测/动作接口下，提高严格任务成功率；
同时报告成本、终止分布、环境错误和非预期状态修改。

不要直接用“最短轨迹”替代成功：检查信息、等待加载和纠错可能需要合理的额外操作。也不要一开始把许多成本项混成单个奖励；先测清它们与成功的关系，再用消融决定权重。

9.5.3 为什么把 progress 做差分还不够

设 p_t 为第 t 步后的子目标进度。若定义：

r_t = p_t − p_(t−1)
Σ_t r_t = p_T − p_0

求和会消去中间项。如果仍把这个总和变成一个轨迹优势并广播，步骤间依旧没有由过程进度产生的差异化优势；共享同一个优势值，并不意味着不同步骤的策略梯度相同。要完全复现旧奖励，还须保留初始进度以及原先的终止、答案和副作用处理；不能把上式直接当现有 reward 的等价改写。

势函数塑形的标准形式是 F_t＝γΦ(s_(t+1))−Φ(s_t)。折扣求和后为 −Φ(s_0)＋γ^TΦ(s_T)。在相同起点、终止势为零等条件下，它只是一个常数；继续用于组内终态广播时可能被中心化抵消。一般的正向进度奖金并不自动拥有策略不变性保证。Ng、Harada 与 Russell，1999

9.7.3 Judge 与环境也是实验对象

基于状态的规则 judge 可检查真实业务结果，但仍可能存在遗漏。应设计少量针对性的反例：错误对象、只改页面不改数据、完成后撤销、重复执行、部分字段正确、提前 COMPLETE、跨 App 副作用。对照人工轨迹审计，检查假阳性与假阴性。

完整重置应验证业务状态、导航栈、焦点、键盘、模拟时间和权限等。评测时隐藏状态可由 judge 使用；若把隐藏状态直接传给 actor，必须另标输入协议。只统计“环境正常”的成功率会掩盖系统可靠性：可补充条件分析，但主表仍保留所有预先指定任务和失败原因。

9.8值得延伸思考的方向+

9.8.1 端到端模型还是模块化系统

SeeClick/UGround 把定位作为可训练接口，Agent S2 强调分层规划与专家模块；UI-TARS 系列则探索更统一的视觉动作模型。模块化方便定位错误、替换 grounder 和控制成本，但模块之间的目标描述可能丢信息；端到端减少手工接口，也更难区分能力瓶颈。UGround、Agent S2、UI-TARS

对本项目可先保持同一个 4B actor，增加可审计的任务记忆与动作结果记录；若确认大多数错误来自定位，再考虑专门 grounder。比较时固定高层计划，并把额外模型、调用次数与延迟计入成本。

9.8.2 有 API 还需要 GUI Agent 吗

GUI 为没有开放 API 或业务接口不统一的应用提供可见操作入口；API 则能减少部分操作的歧义和步数。二者可以组成混合系统，但动作空间与可靠性条件变了。

OpenMobile2 将模拟移动环境、模拟器环境和 App 原生工具结合，适合作为“纯视觉基准之外的产品路线”阅读。其工具调用成绩不能直接作为纯截图坐标策略的同协议比较；MobileGym 中供任务初始化/判题的内部 API 也不是 actor 自动获准使用的工具。OpenMobile2

可以设计独立实验：纯 GUI、GUI+同范围公开工具、工具失败后的 GUI fallback。比较严格完成、时延、工具权限、失败可恢复性，而不是只用动作数更少证明模型能力更强。

9.8.3 既然有模拟器，还要不要学 world model

WM-R1 用学习的 GUI 世界模型生成可交互的后续状态，并支持想象与策略学习。这能扩充训练交互，但策略收益受转移预测、渲染一致性和结果评价误差影响；生成画面像真的，不代表业务状态真的正确。WM-R1

MobileGym 已有程序实现的环境和结构化状态，当前先利用可验证的真实环境 rollout 通常更直接。若长尾 App 或真实设备交互昂贵，再考虑 learned world model，并做“一步预测一致性→多步漂移→真实环境策略收益”的逐级检验。世界模型中的成功率不能替代真实或程序环境成功率；训练策略还可能主动利用模型漏洞。

9.8.4 Sim-to-real 的关键是覆盖什么差异

需要分别检查布局/字体、设备尺寸、软键盘、异步等待、系统弹窗、权限、网络错误、应用状态和动作时延。对这些因素做可控随机化，有助于研究稳健性；随机化范围应来自目标设备的实际差异，过度随机化也会增加学习难度。

MobileGym 论文对其自身平台的迁移证据不等于你的 checkpoint 已完成真实设备验证。简历应保留“浏览器模拟移动环境”口径；有相同任务语义、明确映射和真实设备复测后，再写 sim-to-real 结果。MobileGym

9.8.5 不确定性、停止和交互安全

停止也是动作选择的一部分。模型应能区分“完成证据充分”“仍可恢复”“无法完成”；仅增加 ABORT 惩罚可能诱发胡乱点击，仅惩罚 false-COMPLETE 也可能增加放弃。应同时观察严格成功、误报、漏报、恢复和成本。

在真实应用中，页面内容还可能包含与用户目标冲突的指令；可研究将页面视为数据、限制高影响操作、在不确定时请求用户确认。但这应另设任务与威胁模型，本项目尚未验证相关能力，不能写成已经实现的安全保障。

9.9面试延伸问答 12 个能展开讨论的问题+

以下 R01–R12 是在前面 30 个项目问答之外新增的研究问题。回答用“已经观察到什么—如何解释—如何证伪”组织；涉及改进时明确是计划。

R01 你怎样定义 GUI Agent，它和普通视觉问答有什么不同？

回答思路： 它是通过有限观察持续改变环境状态的决策任务。截图只显示状态的一部分，动作会影响后续可见信息、可执行选项和最终业务结果，所以要联合考虑 grounding、状态估计、计划、恢复和终止。视觉问答主要评价当前答案，GUI 还要评价整段交互的结果与代价。

追问准备： 用跨 App 复制联系人信息举例：源页面离开后关键信息不可见，记忆直接影响后续动作。可对照当前截图、近期多图和结构化记忆；不能只因为跨 App 分数低就断言记忆不足。

R02 Grounding 准确率很高，为什么整任务成功率仍然很低？

回答思路： “点中了所说的按钮”不保证“这个按钮是当前该点的”。还存在目标理解、动作顺序、隐藏状态、执行时序和终止错误。长序列会积累失败风险，但独立同分布误差模型只是解释用的简化。

追问准备： 将动作意图与坐标分开标注，使用正确意图/坐标的诊断对照，找最早偏离点。不要把离线 point-in-box 指标和在线 strict pass@1 放在一个榜单排序。

R03 给模型更多历史截图一定更好吗？

回答思路： 历史可能补充页面变化和已离开的实体，也会带来视觉 token、干扰和上下文压缩问题。关键是保留与当前决策相关的证据，而不只是增加窗口长度。

追问准备： 冻结 actor 比较文本历史、最近截图、结构化记忆、混合记忆；测跨 App 成功、事实保持与成本。记忆摘要应标注来源步骤和置信度，错误信息需要可更新；不能把 ground-truth 隐藏状态写进纯视觉记忆。

R04 SFT、DPO 和在线 RL 分别适合解决什么？

回答思路： SFT 建立接口、基础技能和恢复行为；DPO 需要同一上下文下可解释的偏好对；在线 RL 在可执行环境中直接优化结果和交互决策。三者的数据来源与失败模式不同，不能用算法名称替代问题诊断。

追问准备： 如果格式错误很多，先做数据与 SFT；基础行为可用但完整任务欠佳，再考虑在线反馈。UI-TARS 的 Agent DPO、InfiGUI-R1 的 RLOO 与 UI-TARS-2 的 PPO 应准确区分，不能统称 GRPO。

R05 你现在的 reward 是 PRM 吗？有部分分为何还不算？

回答思路： 当前是最终状态的规则评分，可以给部分目标达成分，但没有使用学习得到的过程评分器。PRM 需要说明训练数据、预测对象与使用位置，也可以复用已有评分模型；逐步调用一个终态检查也只是规则过程信号。

追问准备： 继续检查 reward 怎样进入 advantage。当前路径将轨迹优势广播；即使新增 Step.reward 字段，也要贯通训练消费链路，才能声称实现逐步信用。

R06 为什么把 progress 相邻作差，不一定改进信用分配？

回答思路： 差分求和仍是终点减起点，如果最后又变成一个轨迹标量并广播，没有新增由过程进度产生的动作优势差异；各动作本身的梯度仍可能不同。信用分配要使不同决策获得不同的回报估计或 baseline。

追问准备： 画出 reward→return→advantage→token mask 的链路，给出 telescoping 等式。势函数塑形的策略不变性有条件；新局部辅助项应做零系数一致性与副作用审计。

R07 同一截图下比较动作，是否就是 GiGPO？

回答思路： 不够。GiGPO 的局部比较依赖足够可比的决策状态与后续 return。相同截图可能对应不同表单草稿、任务参数、历史信息或剩余预算；视觉相似可能制造错误的优势。

追问准备： 先统计可靠 anchor 的覆盖、不同轨迹数和 return 方差。若严格匹配后覆盖很低，就转向子目标段或 value；不能通过随意粗化状态来获得漂亮覆盖率。其视觉小环境实验也不能直接证明手机 GUI 迁移。

R08 为什么不直接训练一个更大的 PRM？

回答思路： 更大的模型不会自动消除标签含糊、隐藏信息缺失和奖励利用。当前环境已经能提供可验证状态，先证明过程标签优于 outcome 基线，再判断是否需要把它蒸馏为图像评分器。

追问准备： PRM 离线相关性、校准、候选排序和在线策略收益分别测。冻结 actor 的重排收益包含额外搜索预算；AgentPRM 的末步轨迹奖励实验也不能当作 dense 更新证据。

R09 当前实验支持哪些结论，不支持哪些？

回答思路： 同一 FCzero run 在固定任务 ID 与题目文本下，从 23/256 到峰值 56/256，支持该次训练过程中验证表现改善。跨 App 与高难任务仍弱，后期回落提示稳定性和终止行为值得追踪。

追问准备： 不能由此证明 FCzero 优于普通 GRPO，不能报多 seed 稳定提升，也不能把六组配置差异较大的历史 run 当严格消融。补做共同初始化、同协议、等预算对照及新 hold-out。

R10 多采几个候选再让 verifier 选，算性能优化吗？

回答思路： 算系统推理优化，但要分别报告额外计算收益和 policy 参数更新收益。候选、重试和环境回退次数都应纳入预算，且 selector 只能使用协议允许的信息。

追问准备： 比较单次 actor、同候选数随机选择、verifier 选择，使用相同初态和预算；没有可恢复状态时，不能假装各候选都在同一状态真实执行过。

R11 如果面试官说模拟器太简单，你怎么回答？

回答思路： 模拟器的价值是可控初态、状态判题、可复现交互和低成本实验，适合研究后训练机制。它与真实设备在异步、布局、应用业务和错误分布上可能不同，需要单独验证外部有效性。

追问准备： 先在模拟器内做受控扰动与 held-out App，再选有明确任务对应关系的真实设备测试。当前应坦诚尚未得到本 checkpoint 的真实设备迁移结果。

R12 资源只够再做两组实验，你会怎么选？

回答思路： 先修到冻结基线可复现，这是测量前提。然后根据失败审计选一个主因素：若信息丢失占主因，做原历史 vs 近期多图/记忆；若过程监督明确且映射可靠，做原 GRPO vs 单一局部信用项。

追问准备： 固定 task、初态、初始化、奖励和预算，预先指定 strict pass@1 与跨 App 分层结果，报告成本和失败模式。两组、单 seed 的结果只用于方向筛选，不承诺统计显著或最终产品收益。

9.10.1 建议按问题阅读，而不是背排行榜

  1. 任务是什么： AndroidWorld + MobileGym。先看 observation/action、初始化、judge 与预算，画出训练闭环。
  2. 模型究竟哪里出错： SeeClick + ScreenSpot-Pro + UGround。理解 grounding 的独立指标与高分辨率条件。
  3. 数据如何成为能力： UI-TARS + OSGenesis。区分生成指令、获得成功轨迹、恢复数据与偏好对的成本。
  4. 在线训练怎样改变行为： DigiRL + MobileRL + UI-TARS-2。比较 value/AWR、轨迹 GRPO 与 PPO/GAE；核对输入协议。
  5. 怎样给动作分配信用： GiGPO + GUI-Shepherd + AgentPRM。追踪标签、奖励、advantage 和推理使用方式。
  6. 研究边界如何扩展： Agent S2 + OSWorld2 + OpenMobile2 + WM-R1。讨论长任务、模块化、混合工具与世界模型。
